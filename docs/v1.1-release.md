# dsh-migration-eval v1.1 交付说明（2026-09-29）

> **时点声明**：本文是 **v1.1 交付当时**的记录，数字都是当次真跑出来的。
> v1.1 相对 v1.0 只做了一件事 —— **补上探针请求**，让兼容性门的
> `cache_control 使用` 一项脱离 `not_checked`。
>

## 一、一句话

**v1.1 = v1.0 + 一次真发的探针请求。判定第一次出得了「可迁移」。**

v1.0 的判定被卡死在「有条件迁移」：兼容性门里 `cache_control 使用` 恒为「未检测」，
而判定规则规定"未检测 → 最多有条件迁移"。这一项之所以恒为未检测，是因为它
**静态判不了** —— `cache_control` 由 pi-ai 运行时生成、每次请求必发，配置文件里
永远扫不到；而端点收到后是否兑现，只有发一次请求看计费才知道。

v1.1 把那次请求发了。它叫**探针请求**，代码在 `src/cache-probe.ts`，默认开启。

---

## 二、探的是什么：两分支对照，四个请求

### 2.1 天真的做法会得到假通过

最直觉的设计是"发两次同一前缀，看第二次命中没有"。**这是错的，而且是危险的错**：

> `cache_control` 之外，**DeepSeek 这类端点自己就有自动前缀缓存**。
> 第二次命中完全可能跟那个标记无关。

只发一对请求，得到的结论是"**缓存生效了**"，而不是"**标记生效了**"——
报告里却会写成后者。**它比不检查更糟：它给了一个没有依据的「通过」。**

### 2.2 所以要有对照组

```
  A 分支（带 cache_control）：POST#1 → POST#2（同一前缀）
  B 分支（对照，不带标记）  ：POST#1 → POST#2（另一前缀，免得蹭 A 的缓存）
```

四种组合各有确定含义：

| A 分支第 2 次 | B 分支第 2 次 | 含义 | 处置 |
|---|---|---|---|
| `cache_read>0` | `=0` | 标记是缓存生效的**必要条件** | `pass` |
| `cache_read>0` | `>0` | 端点**自动**缓存，标记不可归因 | `pass` |
| `cache_read=0` | —— | 端点接受标记但**不兑现** | `pass` + ℹ️（成本问题） |
| HTTP 4xx | —— | 端点**拒收** `cache_control` | **`fail`（一票否决）** |

最后一行是唯一否决的情形，理由：harness 每次请求必发 `cache_control`，
端点拒收等于**一次对话都发不出去** —— 那是正确性问题，不是成本问题。

探针还必须**复刻 harness 的请求形状**（`x-api-key` 鉴权、`<baseUrl>/v1/messages`、
`system` 为内容块数组、标记挂在系统块上），否则验的不是同一个东西。

## 三、真实端点验证结果

**2026-09-29，`https://api.deepseek.com/anthropic`，两个模型各发 4 个请求。**
前缀 7000 字符（实测约 2.5k token），冷热之间等 2s（为什么必须等，见第五节）。

### 3.1 四分支原始读数

| 路由 | 分支 | 第 1 次 | 第 2 次（同一前缀） |
|---|---|---|---|
| `deepseek-flash`（**候选**） | 带 `cache_control` | HTTP 200 · in=2490 · **read=0** · write=0 | HTTP 200 · in=186 · **read=2304** · write=0 |
| `deepseek-flash` | 对照（不带） | HTTP 200 · in=2499 · **read=0** · write=0 | HTTP 200 · in=195 · **read=2304** · write=0 |
| `deepseek-v4-pro`（基线） | 带 `cache_control` | HTTP 200 · in=2563 · **read=0** · write=0 | HTTP 200 · in=3 · **read=2560** · write=0 |
| `deepseek-v4-pro` | 对照（不带） | HTTP 200 · in=2566 · **read=0** · write=0 | HTTP 200 · in=6 · **read=2560** · write=0 |

四条的 `in + read` 各自守恒（如 flash 2490 = 186 + 2304），说明 `cache_read`
确实是从"本次输入"里划出去的，不是额外计数。

### 3.2 落进哪一支

**两模型都落在第 2 行：`>0 | >0`。**

1. **没有任何 4xx。** 端点接受 `cache_control`，harness 那三次必发的标记不会把请求打回去。
   → 不触发否决。
2. **`cache_write` 全程为 0** —— 该端点不单列写入档，不额外收写入费。
3. **命中与标记无关。** 同一路由内，带标记与不带标记的 `cache_read` **完全相同**
   （flash 2304 / pro 2560）。对照分支根本没发 `cache_control`，照样命中。

→ 本项判 **`pass`**。

## 四、交叉验证：v3 三批次那 94–99% 的命中率从哪来

这一节回答的是 **v1.0 数据回答不了、只能写"归因不了"的那个问题**。

### 4.1 v1.0 的数据在结构上就答不了

v1.0 记录的观测（`docs/eval-design-constraints.md`、`docs/acceptance-gate-design.md`）：

| 观测 | 输入 token 命中率 |
|---|---|
| v3 三批次 30 次内层运行 | **94.2% – 98.8%**（pro 95.3–98.8，flash 94.2–97.6） |
| 一次相隔数小时的孤立运行 | pro **0.0%**、flash 30.2% |
| v1.1 探针（本次） | flash 2304/2490 = **92.5%**、pro 2560/2563 = **99.9%** |

**为什么三批次的数据答不了**：harness（pi-ai 的 `anthropic-messages` 路由）**每次请求
都无条件发 `cache_control`**。所以那 94–99% 的观测值**全部来自"带标记的请求"**——
数据里**根本没有不带标记的那一格**。没有对照组，归因就只能停在"归因不了"。

v1.1 的探针补的正是这一格。

### 4.2 结论

> **那 94–99% 的命中率来源是端点的自动前缀缓存，`cache_control` 标记的边际贡献为零。**

依据是本报告第 3.1 节那张表：对照分支不发任何 `cache_control`，第 2 次照样命中，
且读到的 token 数与带标记分支**逐字节相同**。若标记有作用，对照分支就该读到 0。

数值上也自洽：探针在 2.5k 前缀上量到 flash 92.5% / pro 99.9%，
与三批次在约 5.5k 前缀上量到的 94.2–98.8% 落在同一区间 —— 同一机制。
（**这只是量级一致，不是同一个数**；两次测量的前缀长度、轮数、是否流式都不同，
见第七节边界。）

### 4.3 这对判定的影响是**正面**的

成本门里"flash 低 53–78%"这个结论，**不依赖一个可能被丢掉的字段**：
它建立在该端点无条件生效的自动缓存上。标记被忽略反而是好事 ——
少一个会被网关剥离、被版本改掉的变量。

**所以本项 `pass` 之后不进风险清单。** 它没有一个"但是"需要读者提防。

> ⚠️ 与 `infoText` 那条出路的区别：`infoText` 是给"端点接受标记但**不兑现**缓存"用的
> ——那是成本优势**不成立**，必须在风险清单里说一句。本次不是那种情况：缓存确实生效了。

## 五、跑真端点时发现的**两个探针自身缺陷**

> 这是 v1.1 最值得记录的部分：**两个缺陷都不会让离线测试变红**，
> 只有真的把请求发出去才会暴露。

### 5.1 冷热请求之间必须**等**

第一版在 `POST#1` 返回后**立刻**发 `POST#2`（间隔亚秒级）。结果：

| 路由 | 冷 → 间隔 → 热 | 结果 |
|---|---|---|
| `deepseek-flash` | 0 / 500 / 1000 / 2000 / 5000 ms | 全部命中 |
| `deepseek-v4-pro` | **0 ms** | **未命中** |
| `deepseek-v4-pro` | 500 / 1000 / 2000 / 5000 ms | 全部命中 |

端点把缓存**写进去**和让后续请求**读得到**之间有延迟。间隔太短时 pro 读到
`cache_read=0` —— **而缓存其实是好的**。那会落进"端点接受标记但不兑现"那一格，
产出一条**假阴性**的成本结论，并以 ℹ️ 风险的形式写进报告。

修法：`runArm` 在冷热之间插 `settleMs`（默认 **2000ms**，是实测阈值 500ms 的 4 倍余量）。
两个分支仍并行，所以整趟只多花约一个 `settleMs`。

### 5.2 前缀不能跨次复用

第一版把前缀种子写死（`0x5eed` / `0xbeef`）。连跑两次就退化 ——
**第二次运行的"冷"请求直接命中上一次留下的缓存**（实测两份缓存都活了 15 分钟以上）。
更糟的是它**能造成假通过**：端点即便已经停止缓存，几分钟前的旧条目在 TTL 内
仍然会应答，探针照样报"缓存生效"。

修法：每次探针用**当次**的随机种子造前缀。内容形状仍是确定性的随机音节，
变的只是种子；两个分支仍各取不同种子。这与本仓库既有口径一致 ——
前缀缓存有 TTL，任何跨轮的绝对量都不可比，探针要测的是**当次**行为。

### 5.3 还有第三个，但不是这次跑出来的

离线回归曾**真的联网**：端到端测试走 `execute()`，而 v1.1 起 `execute()` 内含探针，
测试框架又给环境塞了非空密钥字段。它当时**恰好**因请求失败退成 `not_checked`、
与旧断言一致，所以**测试是绿的** —— 若机器上有可用密钥，它会真的花钱而没人知道。
现由两道兜底挡死：毒药 `fetch`（逃逸即记账并判失败）+ 全局 `DSH_EVAL_NO_PROBE=1`。

## 六、判定措辞的最终版本

### 6.1 四档完整对照

| 探到的情形 | `status` | 报告里的措辞要点 | 风险清单 |
|---|---|---|---|
| 端点**拒收**（HTTP 400/422） | `fail` | 端点拒收 `cache_control`；harness 每次必发 → 一次对话都发不出去 | ⚠️ 一票否决 |
| 鉴权失败（401/403） | `not_checked` | 鉴权问题**与端点能力无关**，不算它头上 | ⚠️ 未检测 |
| 传输层失败 / 200 但无 `usage` / 第 2 次失败 | `not_checked` | 写明为什么没探成，**"没探"不等于"没问题"** | ⚠️ 未检测 |
| 热读 `>0`，对照 `>0` | `pass` | 端点兑现缓存；**但对照分支也命中 → 命中不可归因给标记**；成本优势成立且不依赖该标记 | **不进**（本次实测落这里） |
| 热读 `>0`，对照 `=0` | `pass` | 端点兑现缓存，且**标记是必要条件** | 不进 |
| 热读 `>0`，对照**读不到** | `pass` | 端点兑现缓存；**标记是否必要无法归因**，结论只到"缓存确实生效"这一档 | 不进 |
| 热读 `=0` | `pass` | 端点**接受但不兑现**；不影响请求能否发出，故不否决，**但成本优势不成立** | ℹ️（**不是** ⚠️） |

### 6.2 两条口径，是刻意分开的

- **`fail` 只给正确性问题**（端点拒收请求体）。这一档会一票否决迁移。
- **成本类发现一律不否决。** 这是本仓库的既定论证（`verdict.ts` 文件头：
  「把成本写进否决是范畴错误」）。"缓存不兑现"属于这一档 ——
  它需要一个新的出口：**状态是 `pass`、但仍要在风险清单里说一句**。
  这个出口就是 `infoText`（只被那一种情形使用）。

### 6.3 两次实测覆盖到的档位

- `deepseek-flash` / `deepseek-v4-pro` @ `api.deepseek.com/anthropic` → **热读 `>0`、对照 `>0`**
- 其余档位由离线回归第 16 组用桩 `fetch` 覆盖（26 项断言），**未在真实端点上遇到过**。

## 七、边界：下面每条都必须和第 3、4 节的结论一起读

1. **缓存"有没有"和"有多少"是两回事。** 探针验的是前者。后者受 TTL 影响剧烈波动
   （同一端点上实测 0.0% 与 99.9% 都出现过），仍然**跨轮不可比**。
2. **探针测的是最小请求。** 前缀约 2.5k token、单轮、非流式、`max_tokens=1`。
   真实运行里前缀更长（约 5.5k）、多轮增长、且是流式的 —— 那些条件下的行为探针不覆盖。
3. **它验的是"端点在最小请求上如何反应"，不是"整趟真实负载下如何"。**
4. **只在两个模型、一个端点上验过。** 换端点（尤其不做自动缓存的）结论就会变。
5. **探针不是零 token。** 4 个请求、每次前缀约 2.5k token，实耗写进报告那一项的 `detail`。

## 八、复现指引

### 8.1 离线回归（零成本，不联网）

```bash
cd /Users/mac/dsh-agent-eval
pnpm build && pnpm test:offline     # 16 组 152 项断言
```

### 8.2 复现本次真实端点验证

```bash
eval "$(grep -E '^export ANTHROPIC_AUTH_TOKEN=' "$HOME/.zshrc")"
export DEEPSEEK_API_KEY="$ANTHROPIC_AUTH_TOKEN"
unset ANTHROPIC_AUTH_TOKEN

node --input-type=module -e '
import { probeCacheControl } from "./dist/cache-probe.js"
const r = await probeCacheControl(
  { name: "flash", api: "anthropic-messages",
    baseUrl: "https://api.deepseek.com/anthropic", model: "deepseek-flash" },
  process.env.DEEPSEEK_API_KEY,
  { onAttempt: (a) => console.log(a.arm, a.nth, a.status, JSON.stringify(a.usage)) },
)
console.log(JSON.stringify(r, null, 2))
'
```

或走插件本体（同时验证接线）：

```bash
dsh --profile eval-runner headless --json \
  "只调用 eval_run_dual，suite 填 multi-step/01-single-step，拿到结果后原样输出，不要做任何其他操作"
```
