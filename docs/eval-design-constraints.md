# 评测设计约束

第三阶段（Web UI / 迁移接受门 / 波动测量）开工前必须先接受的约束。全部来自实测，不是推测。

---

## 约束一：成本不可跨运行对比

同一套件、同一 prompt、同一后端，连跑三次：

| 运行 | v4-pro 输入 token | v4-pro 输出 | v4-pro 成本 | v4-pro cache 命中率 | flash 成本 |
|---|---|---|---|---|---|
| 1（间隔后首跑，**冷**） | 5569 | 215 | **$0.004100** | ~0% | $0.000700（命中 24%） |
| 2（紧接着跑，**热**） | 5569 | 253 | **$0.000700** | ~97.8% | $0.000100（命中 97%） |
| 3（紧接着跑，**热**） | 5569 | 141 | **$0.000443** | ~98.8% | $0.000085（命中 98%） |

**`inputTokens` 三次完全一致（方差 0%），成本摆动 5.9×–8.2%。** 差异全部来自 prefix cache 冷热。

命中率是从成本反解的（`cost = miss×miss价 + hit×hit价 + out×out价`，`miss + hit = inputTokens`），三次都落在整数解上，所以不是估算误差。

### 推论

1. **`inputTokens` 不能当稳定性指标。** 一个"三次 inputTokens 差异 < 30% 即视为稳定"的判据，在这组数据上会报告"极其稳定"（实际差异 0%），而成本差了近 6 倍。**抖动藏在 cache 分档里，不在总量里。**
2. **冷跑才接近真实成本。** 热跑会低估近 6 倍。要报"这个套件跑一次多少钱"，必须用冷跑数据。
3. **同一次运行内的两列对比仍然可用。** v4-pro 每次都比 flash 贵 6–8 倍，方向性稳健。报告里的"成本节省 84.1%"只有在两列**同批**跑出来时才成立——这个前提必须写进文档，否则以后有人拿两次不同的运行来比就会得出荒谬结论。
4. **跨运行要对比，就只能比 miss-token**（`inputTokens` 字段减去 `cacheReadTokens`）——它不受 cache 温度影响。或者固定 cache 状态（每轮前先预热），或者报区间而非点值。

### 尚未验证的两条（**未验证，当前设计不依赖此假设**）

下面两条是三次实验覆盖不到、且**没有花钱补实验**的推论。写在这里是为了标明边界，
不是为了让谁去依赖它们。**当前设计不依赖此假设** —— 约束一下面的四条推论、以及
报告里的成本口径，都不需要这两条成立：

- **冷热切换的时间阈值未知**（间隔多久算冷）。三次实验只覆盖了"间隔后首跑"和"紧接着跑"
  两端，中间是空的。若将来要写"预热多久算热"的判据，必须先补实验。
- **命中率与 prompt 长度的关系未测**。当前只有一个 prompt，无法判断命中率是被 prompt
  长度、被 prefix 结构、还是被别的什么决定的。

两条都不影响现在的结论：约束一已经用"跨运行只比 miss-token"绕开了对它们的依赖。

## 约束二：单步的 token 用量只有 step 结束才可见

`usage` 只在 `status`/`phase: "step_end"` 事件上出现，**每步一条、增量式**。
预算检查因此只能逐步做：一个巨型 step 仍可能冲破上限。

---

## 约束三：断言只能依赖 `final`

NDJSON 里除 `final` 外，字符串与对象键超 **8 KiB 会被截断并标 `truncated`**，单行超 32 KiB 会丢结构化字段。
拿 `tool_result` 做 `output_contains` 判断，会把"输出了但被截断"误判成失败。`final` 不设上限。

---

## 约束四：不读落盘 trace

`~/.dsh/sessions/<项目>/<sessionId>/session.v4.jsonl.zstd` 有三个坑（多 frame zstd / usage 双重计数 / 需要额外依赖），而 NDJSON 里什么都有。绕开。

## 第三阶段测量协议（波动测试）

第三阶段开工前先跑这个。目的不是"再确认一遍成本会抖"——约束一已经证明了；目的是拿到
**这一个套件**的抖动幅度，用它来定 `max_steps` 阈值和成本对比的可信区间。

### 命令

```sh
cd /Users/mac/dsh-agent-eval
source ~/.zshrc          # 需要 DEEPSEEK_API_KEY 已导出
./test/run-variance.sh   # 默认连跑 3 次；VAR_RUNS=5 可改次数
```

脚本做三件事：跑 N 次端到端 → 从每次的 NDJSON 里取出工具报告 → 汇总到
`/tmp/variance-<时间戳>/summary.txt`。原始 NDJSON 留在同目录，**只供本机复查，不要提交**。

### 要记录的四项指标

| 指标 | 从哪来 | 拿它干什么 |
|---|---|---|
| `inputTokens` | 报告「输入Token」行 | 判断 prompt/上下文是否稳定（注意：它对 cache 温度**不敏感**） |
| `outputTokens` | 报告「输出Token」行 | 判断模型输出长度是否稳定 |
| **step 条数** | 报告「平均步数」行 | 定 `max_steps` 阈值的**唯一**依据 |
| `costUSD` | 报告「成本(USD)」行 | 估成本区间；**不可**用点值做跨运行对比 |

> 「平均步数」在套件只有 1 个用例时就是该用例的 `step_end` 条数。多用例套件下它是均值，
> 需要逐用例条数就得拆开跑或另出报表 —— 当前套件是单用例，不受影响。

### 三次数据的用途

1. **定 `max_steps` 阈值。** 现在的 `value: 5` 是拍的，不是测的。
2. **定成本对比的可信区间。** 报告里的成本应写成区间（如 `$0.0004 – $0.0041`）并标注首次
   （冷）值，而不是单次跑出来的那个数。

### 判断标准

- **若三次 `step_end` 条数极差 > 3** → `max_steps` 断言需要放宽，或改成
  **「步数中位数 ± N」**，否则断言本身就在随机失败。
- 若极差 ≤ 3 → 维持当前阈值。脚本会自动打印这条判据的结论。
- **成本**：脚本会同时打印「输入Token 极差」。**如果它 < 30% 而成本仍在数倍摆动，
  不要误读成"稳定"** —— 那正是约束一描述的情形。

### 跑完之后

把 `summary.txt`（**不是**原始 NDJSON）连同结论一起提交到 git，并回填本文件约束一的表格。

### 报告口径（沿用，勿改）

1. 成本报告写**区间**，标注首次（冷）值。
2. 迁移接受门的**成本判据用 miss-token 差**，不用成本差。
3. 报"成本节省 X%"时，强制校验两列来自同一次运行（`generateComparison` 只在同批数据上调用，
   这是代码层面的保证；人工比两次不同的运行则会失效）。
