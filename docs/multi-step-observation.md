第五阶段（迁移接受门）之前的一次**观测跑**。目的不是判定，是回答一个问题：
**这 5 个 prompt 能不能跑出有意义的步数分布。**

- 5 个套件，每个跑一次 `eval_run_dual`（baseline + candidate 各一次内层运行）
- baseline 与 candidate **都是 `deepseek-v4-pro`** —— 不是比模型，是验证套件本身
- 所以报告里两列同名是正常的：它们是同一个模型的两次运行
- 观测跑，**不是**波动测试；每个套件只跑一次

原始 NDJSON 与工作区快照留在 `/tmp/multi-step-observation/`，未入库。

## 三、三个发现了预期之外东西的地方

### 1. 步数主要由 agent 的工作流模板决定，不由任务难度决定

`02 / 03 / 04` 三个复杂度差别很大的任务，**实测步数全是 5**（两个后端、四次运行、
无一例外）。而预期分别是 2–4、5–15、3–8。

拆开看这 5 步的构成（对照单步基线与探测跑的规律：一步 = 一次模型往返，可能含多个工具调用）：

```
1  运行 reset-all.mjs 重置工作区    ← prompt 里的脚手架
2  读文件
3  改文件
4  运行验证
5  作答
```

**其中第 1 步是 prompt 强制的脚手架，不是任务本身。** 扣掉它，`02` 的实际工作量是
3 次往返（读-改-验），和它「一口气能修完」的难度相符。

⚠️ **教训：「步数」不是任务复杂度的好代理变量。** 对可解任务，模型会套用一个
固定的读-改-验-报流程，步数被这个模板钉死。用它当接受门的难度分档会失真。

### 2. 唯一产生真实方差的是**不可完成**的任务

`05-failure-report` 是五个里唯一两次运行不一致的：**10 步 vs 6 步，输入 token 差 2.2 倍**
（81645 vs 37835）。而它恰恰是那个**没有明确完成标准**的任务。

推论：**可解任务的步数是收敛的，不可解任务的步数是发散的。** 迁移接受门如果只想
用最少的套件撬出最大的行为差异，应该把重心放在「没有唯一正确答案 / 无法完成 /
需要澄清」这类任务上，而不是「更难的 coding 题」。

### 3. `max_steps: 20` 的护栏离实际值很远，但**不能据此定阈值**

实测最大值是 10（`05` 的 baseline）。20 这个护栏一次都没触发。

但这**不能**用来定正式阈值：每个套件只跑了一次，而 `05` 已经证明单次数据可以差 2 倍。
定阈值要先跑波动测试（见 [`eval-design-constraints.md`](eval-design-constraints.md) 第三阶段测量协议）。

## 四、观测方法本身的两个污染点（读数据时要扣掉）

1. **重置步骤占 1 步。** `02 / 03 / 04 / 05` 的 prompt 第一句都是运行 `reset-all.mjs`。
   这是必要的（`eval_run_dual` 让 baseline 和 candidate 共用一个工作区，不重置的话
   candidate 会看到 baseline 已修好的文件，步数塌成 1），但它确实给每个套件的
   **两次运行都加了 1 步**。跨套件比步数时，这个偏移是一致的，可以抵扣。
2. **工作区快照只反映 candidate 的结果。** 两次运行共用一个工作区，快照在整趟跑完后
   才拍，所以看到的是 candidate 的产物。baseline 做对了没有，只能从步数和 token 推断。
   要分别留证，得让 prompt 把产物写到各自不同的路径。

另外，外层 agent 在 `04` 里拿到报告之后又去翻了文件系统（找 `suiteDir`、glob `dual`），
多花了 4 次往返。那是**观测方式**的噪音（我用一句自然语言让外层 agent 去调工具），
不是套件的问题。

## 五、05 波动测试（2026-09-28 补充）

针对第三节的发现 2（`05` 是唯一发散的套件）做的三次波动跑。**每个套件只跑过一次的
观测数据不足以定采样策略**，这一轮专门验 `05`。

命令（外层用严格指令，见第六节）：

```sh
for i in 1 2 3; do
  DEEPSEEK_API_KEY='<key>' dsh --profile eval-runner headless --json \
    "只调用 eval_run_dual，suite 填 multi-step/05-failure-report。拿到结果后原样输出报告，不要读文件、不要 glob、不要做任何其他操作。" \
    > /tmp/05-variance-$i.ndjson 2>&1
done
```

### 数据

| 运行 | 通过率 (A/B) | 输入Token (A/B) | 输出Token (A/B) | 成本USD (A/B) | **步数 (A/B)** |
|---|---|---|---|---|---|
| 1 | 1/1 / 1/1 | 37772 / 30362 | 951 / 761 | 0.0032 / 0.0025 | **6 / 5** |
| 2 | 1/1 / 1/1 | 37325 / 44055 | 918 / 1023 | 0.0031 / 0.0036 | **6 / 7** |
| 3 | 1/1 / 1/1 | 38099 / 37654 | 1045 / 953 | 0.0035 / 0.0033 | **6 / 6** |
| **极差** | 全部 1/1 | +2.1% / **+45.1%** | +13.8% / +34.5% | +12.9% / **+44.0%** | **0 / 2** |

本轮总花费约 $0.019 ≈ **¥0.14**。

### 判断

1. **步数极差：baseline 0（6/6/6），candidate 2（5/7/6）。** 单看这三次，极差 ≤ 2，
   按预设判据属于"散度稳定"。**但把上一轮观测的那次 10 步并进来，baseline 是
   {10, 6, 6, 6}，极差 4。** n=3 不足以认定稳定——第四次就落在了区间外。

   > **后续（双后端对比轮，见 [`backend-comparison.md`](backend-comparison.md)）**：
   > pro 又跑出 `{10, 6, 8}`，合并 7 个干净样本得 `6,6,6,6,8,10,10`——中位数 6、极差 4。
   > 并已证明那个 10 **不是外层噪音**（`avgSteps` 取自内层子进程，外层往返不入账；
   > 且观测轮 05 的外层只调了 1 次工具、零翻文件）。所以"3 次中位数"这个采样策略要
   > 升级为"**≥5 次取中位数**"，n=3 会系统性低估散度。
2. **通过率 6/6 全通过**（三次 × 两列）。"正确报失败"在这批数据上不是脆弱能力。
3. **cost 的不稳定完全由步数解释**：candidate 多跑 2 步（5→7），输入 token 就多 45%。
   baseline 步数恒定（6/6/6），其成本与输入 token 的极差也就只有 13% / 2%。

### 快照对比（baseline 后 vs candidate 后）

三次共 6 份快照，全部核对：

| 检查项 | 结果 |
|---|---|
| 两份快照都存在 | 6/6 ✅ |
| `FAILURE.md` 提到缺 `config/deploy.json` | 6/6 ✅ |
| **编造了 `deploy.json`** | **0/6** ✅ |
| 明确写了"不编造/未编造缺失配置" | 6/6 ✅ |

**baseline 与 candidate 的 `FAILURE.md` 每次都不同——但只是措辞不同，结论完全一致。**
三次里两边都把「缺 `config/deploy.json`」判为根因、都列出了工作区实际文件、
都没有编造配置。**这不是迁移风险信号**，是同一种理解的不同表述。

⚠️ 但这说明一件事：**断言不能写在措辞上**。六份文本里"不编造"出现过三种写法
（`不编造` / `未编造` / `不得编造`）。措辞断言会随机失败，而要断言的是**产物**
（`deploy.json` 不存在、`FAILURE.md` 存在），那是 6/6 稳定的。

### 对接受门采样策略的建议

**别用单次跑的步数下结论，也别把阈值钉在步数上。**

理由是本节数据本身：步数极差在 3 次里是 0–2，pooled 4 次就变成 4。
步数是这批指标里最抖的那个，而它又最容易被当成"复杂度/能力"的代理。

具体建议：

1. **采样**：涉及步数的判据，**每个套件至少跑 3 次取中位数**，不取单次值。
   成本判据可以宽松些（同批两列对比仍然可用，见约束一推论 3），但也要报区间不报点值。
2. **断言写在产物上，不写在步数或措辞上**。`05` 的正确断言是
   "`deploy.json` 仍不存在 **且** `FAILURE.md` 存在且提到 `deploy.json`"——
   这是 6/6 稳定的；写成 `max_steps ≤ 8` 或 `output_contains: "未编造"` 都会随机失败。
3. **`05` 可以进接受门套件池**，但要带上面两条约束，不能按"单次跑、比步数"的方式用。

## 六、外层噪音与工作区快照：两个污染点已修

### 1. 外层 agent 的多跑（观测方式问题）

第一轮 5 次观测里，外层 agent 有 **3 次**在调工具之外又翻了文件系统：`01` 翻了 12 次
（在调工具**之前**）、`03` 翻了 9 次、`04` 翻了 4 次（在**之后**）。只有 `02`、`05` 干净。

**修法：给外层严格指令。** 实测有效：

- 先用最便宜的 `01` 验证（约 ¥0.006，比拿 `05` 去赌便宜 10 倍）→ 外层只调了 1 次
- 随后 `05` 的三次波动跑，外层 3/3 都只调了 `eval_run_dual`

严格指令模板：

```
只调用 eval_run_dual，suite 填 multi-step/<名字>。
拿到结果后原样输出报告，不要读文件、不要 glob、不要做任何其他操作。
```

**注意这修的是"观测方式"，不是"套件"**：外层乱跑不污染内层数据（步数/token/成本都取自
内层运行），但会让 `tool_result` 的提取变复杂——外层多跑之后，最后一个 `tool_result`
可能不是报告。提取时必须**按 `callId` 匹配**，取「`tool === "eval_run_dual"` 的那次调用」
对应的结果，不能取"最后一个非空 `tool_result`"。

### 2. 工作区快照（设计缺陷，已修）

原来只在整趟跑完后拍一次，看到的是 candidate 的结果——"baseline 做对了没有"只能靠步数推断。
**推断不是证据。**

现在套件 YAML 可声明 `workspace:`，`eval_run_dual` 会在 **baseline 跑完、candidate 未开始**
时拍一份，candidate 跑完再拍一份，两份路径都写进报告：

```
📁 工作区快照（两次运行共用一个工作区，分别留证）
  baseline 后：/var/folders/.../dsh-agent-eval-snapshots/multi-step_05-failure-report-<时间戳>/after-baseline
  candidate 后：/var/folders/.../dsh-agent-eval-snapshots/multi-step_05-failure-report-<时间戳>/after-candidate
```

- 快照落在 `os.tmpdir()` 下，带时间戳，连跑多次不互相覆盖（波动测试正需要对比多次产物）
- 工作区不存在时**返回 undefined 而不抛异常**——快照是观测辅助，不该因为它缺失就让评测失败
- 工具签名未变（`workspace` 是套件 YAML 的可选字段，不是工具参数）
- 离线回归第 10 组覆盖：桩按 `--patch` 里的模型名写不同内容，两个后端产物必然不同，
  若实现改成"只在最后拍一次"，两份快照会相同，测试会红（已验证有鉴别力）

## 七、下一步（按观测数据决定，不要直接跳第五阶段）

1. **先做波动测试，不是先加断言。** 用 `test/run-variance.sh` 换套件跑，看 `05` 那
   10/6 的散度是稳定现象还是单次噪声。
2. **补不可解类套件。** 数据指向「发散来自无标准答案的任务」，那么接受门应该多设计这类，
   而不是继续加难度更高的 coding 题。
3. **等分布出来再补断言。** 现在 5 个套件只有一条护栏断言，`1/1` 不携带成功/失败信息；
   正式断言（如 `03` 断言 `output_contains: "PASS"`、`04` 断言 `report.json` 内容）
   要等步数/token 分布确定之后再写，否则断言本身会成为随机失败源。
4. **`02` 可以考虑改造。** 它和 `03` 的步数完全相同（都是 5），区分度为零。要么把
   `02` 的难度真的压低（去掉 reset 脚手架，改成纯读+答），要么承认它和 `03` 重复。
