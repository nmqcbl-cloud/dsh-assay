第五阶段（迁移接受门）之前的一次**观测跑**。目的不是判定，是回答一个问题：
**这 5 个 prompt 能不能跑出有意义的步数分布。**

- 5 个套件，每个跑一次 `eval_run_dual`（baseline + candidate 各一次内层运行）
- baseline 与 candidate **都是 `deepseek-v4-pro`** —— 不是比模型，是验证套件本身
- 所以报告里两列同名是正常的：它们是同一个模型的两次运行
- 观测跑，**不是**波动测试；每个套件只跑一次

## 三、三个发现了预期之外东西的地方

### 1. 步数主要由 agent 的工作流模板决定，不由任务难度决定

`02 / 03 / 04` 三个复杂度差别很大的任务，**实测步数全是 5**（两个后端、四次运行、
无一例外）。而预期分别是 2–4、5–15、3–8。

拆开看这 5 步的构成（对照单步基线与探测跑的规律：一步 = 一次模型往返，可能含多个工具调用）：

```
1  运行 reset-all.mjs 重置工作区    ← prompt 里的脚手架
2  读文件
3  改文件
4  运行验证
5  作答
```

**其中第 1 步是 prompt 强制的脚手架，不是任务本身。** 扣掉它，`02` 的实际工作量是
3 次往返（读-改-验），和它「一口气能修完」的难度相符。

⚠️ **教训：「步数」不是任务复杂度的好代理变量。** 对可解任务，模型会套用一个
固定的读-改-验-报流程，步数被这个模板钉死。用它当接受门的难度分档会失真。

### 2. 唯一产生真实方差的是**不可完成**的任务

`05-failure-report` 是五个里唯一两次运行不一致的：**10 步 vs 6 步，输入 token 差 2.2 倍**
（81645 vs 37835）。而它恰恰是那个**没有明确完成标准**的任务。

推论：**可解任务的步数是收敛的，不可解任务的步数是发散的。** 迁移接受门如果只想
用最少的套件撬出最大的行为差异，应该把重心放在「没有唯一正确答案 / 无法完成 /
需要澄清」这类任务上，而不是「更难的 coding 题」。

### 3. `max_steps: 20` 的护栏离实际值很远，但**不能据此定阈值**

实测最大值是 10（`05` 的 baseline）。20 这个护栏一次都没触发。

但这**不能**用来定正式阈值：每个套件只跑了一次，而 `05` 已经证明单次数据可以差 2 倍。
定阈值要先跑波动测试（见 [`eval-design-constraints.md`](eval-design-constraints.md) 第三阶段测量协议）。

## 四、观测方法本身的两个污染点（读数据时要扣掉）

1. **重置步骤占 1 步。** `02 / 03 / 04 / 05` 的 prompt 第一句都是运行 `reset-all.mjs`。
   这是必要的（`eval_run_dual` 让 baseline 和 candidate 共用一个工作区，不重置的话
   candidate 会看到 baseline 已修好的文件，步数塌成 1），但它确实给每个套件的
   **两次运行都加了 1 步**。跨套件比步数时，这个偏移是一致的，可以抵扣。
2. **工作区快照只反映 candidate 的结果。** 两次运行共用一个工作区，快照在整趟跑完后
   才拍，所以看到的是 candidate 的产物。baseline 做对了没有，只能从步数和 token 推断。
   要分别留证，得让 prompt 把产物写到各自不同的路径。

另外，外层 agent 在 `04` 里拿到报告之后又去翻了文件系统（找 `suiteDir`、glob `dual`），
多花了 4 次往返。那是**观测方式**的噪音（我用一句自然语言让外层 agent 去调工具），
不是套件的问题。

## 五、下一步（按观测数据决定，不要直接跳第五阶段）

1. **先做波动测试，不是先加断言。** 用 `test/run-variance.sh` 换套件跑，看 `05` 那
   10/6 的散度是稳定现象还是单次噪声。
2. **补不可解类套件。** 数据指向「发散来自无标准答案的任务」，那么接受门应该多设计这类，
   而不是继续加难度更高的 coding 题。
3. **等分布出来再补断言。** 现在 5 个套件只有一条护栏断言，`1/1` 不携带成功/失败信息；
   正式断言（如 `03` 断言 `output_contains: "PASS"`、`04` 断言 `report.json` 内容）
   要等步数/token 分布确定之后再写，否则断言本身会成为随机失败源。
4. **`02` 可以考虑改造。** 它和 `03` 的步数完全相同（都是 5），区分度为零。要么把
   `02` 的难度真的压低（去掉 reset 脚手架，改成纯读+答），要么承认它和 `03` 重复。
