## 一、判定分层

**两层一票否决 + 一层建议性。步数门已删除**（2026-09-28，三批次数据判定其无存在价值）。

```
① 质量门     产物判据必须全部通过          ← 一票否决
② 兼容性门   已知兼容性问题必须全部清空      ← 一票否决
──────────────────────────────────────────
③ 成本门     候选成本显著低于基线           ← 建议性
（步数 —— 已删除，只作诊断字段输出）
```

**适用范围**：`01-single-step` 是**烟雾测试，不参与任何判定**（见下）。

### ⓪ 适用范围与烟雾测试

| 套件 | 定位 | 进判定吗 |
|---|---|---|
| `01-single-step` | **烟雾测试（环境探针）** | ❌ **不进** |
| `02` ~ `05` | 质量判据载体 | ✅ 进 |

`01` 验证的是**环境可用**：插件能被 `dsh` 加载注册、YAML 能解析、单步能跑通、
模型能发现并调用 `eval_run_dual`。它**不验证质量**——没有工作区、没有产物，
唯一内容判据是 `output_contains: "Harness"`，查的是**措辞**，
而措辞正是本设计论证过不该进断言的东西。

**不加落盘产物**：加了它就会变成第二个 `02`，失去"单步探针"的区分度。
它在三批次共 9 次运行里都通过，但那是运气不是保证——**不能读成质量证据**。

### ① 质量门（一票否决）

判据是**工作区产物**，不是 `passed/total` 那个数字，也不是步数、措辞、成本。

产物判据已由 `src/artifact-assert.ts` 实现并可自动判定（第四.2 节）。
三批次共 54 份产物判据全部通过（免费复核脚本对 82/82 份累积快照独立确认），
自动判定与人工核对零分歧。

理由见 [`backend-comparison.md`](backend-comparison.md)：产物判据跨轮稳定，
而步数会出现**方向级**的轮间反转（第七.3 节），措辞则有"不编造/未编造/不得编造"三种写法。

### ② 兼容性门（一票否决）

见第五节。**已实现**（`src/compatibility-check.ts`），**静态检查、零 token**。
两个检查项：`system 字段格式`、`cache_control 使用`。

### ③ 成本门（建议性）

候选总成本低于基线总成本即通过。三批次合并 n=9，flash 低 **53–78%**。

**明确定位：成本门不否决迁移，只影响"是否值得迁"。** 它不携带正确性信息——
一个把任务做错的模型可能非常便宜。

采样：**报区间与中位数，不报点值**（05 上 pro 三次是 0.0071 / 0.0036 / 0.0060）。
成本是**唯一**可跨轮使用的指标——三批次 5 套件 **15/15 判定全部一致**，无一例外。

### ④ ~~步数门~~ —— 已删除

**2026-09-28 删除。理由：步数不稳定 + 不进判定 = 没有存在价值。**

三批次（同一配置、相隔 20 分钟）的实测：

| 套件 | v1 判定 | v2 判定 | v3 判定 |
|---|---|---|---|
| 03 | 不重叠 | 不重叠（**反向**） | 重叠 |
| 05 | 重叠 | 不重叠 | 重叠 |
| 02 / 04 | 重叠 | 重叠 | 重叠 |

**同一配置，三批三个判定。** 03 的 pro 批次中位是 `7 / 5 / 7`（批间极差 2），
而它要测的 pro-flash 差距本身只有 1–2 步——**信噪比 ≈ 1**，
"显不显著"基本由某一次运行有没有多跑一步决定。

（本节初稿写的是"按模型分别标定阈值"，依据是 v1 里 03 上 pro 稳定 7 步。
v2 变成稳定 5 步、方向反转。**不是"标定得不对"，是这个指标本身没有测量能力。**）

**保留为诊断字段**（随报告输出，**不设阈值、不出判定**），用途两个：

1. 发现异常漂移（例如候选步数突然翻倍 → 提示可能有重试循环）
2. 成本变化的归因（成本变化来自单价还是来自行为）

## 二、采样策略：只做轮内对比

> **2026-09-28 定稿。** v1/v2/v3 三批次数据推翻了本节最初的「步数 n≥5」规则，
> 代之以一条更强的原则。数据见 `docs/backend-comparison.md` 第七、八节。

### 2.1 核心原则

> **一次 `eval_run_dual` 调用内，baseline 和 candidate 是同批跑的。
> 批次效应作用于整个批次，两列同时受影响 —— 所以轮内对比稳健。
> 跨轮绝对值、跨轮对比都不可靠。**

这条原则直接决定接受门的**输出语义**：

- ❌ 不是「pro 是 X 步，flash 是 Y 步」
- ✅ 而是「**在同一批次内，flash 比 pro 少 N 步、成本低 M%**」

批次效应的量级**不需要查清**（模型服务侧对用户不透明：路由到哪个推理集群、
KV cache 状态、温度是否非零，都查不出也控制不了）。设计只需要知道
**它存在、且轮间不可比**——这就够规避了。

### 2.2 三层采样规则

| 判据 | 数据范围 | 采样 | 依据 |
|---|---|---|---|
| **质量门**（产物判据） | **仅轮内** | n=1 | 产物有确定性，重复跑不增加信息；三批次共 54 份判据全对 |
| **兼容性门** | **仅轮内** | **静态检查（零 token）+ 探针请求（v1.1，4 个请求）** | 静默失败必须当场看见，不能靠历史数据推断 |
| **成本门** | **可用跨轮** | n≥3，**报区间不报点值** | 成本差距来自**单价**，单价不随批次漂移（三批次稳定省 53–78%） |
| ~~步数门~~ | — | **不判定，仅记录** | 已删除，见 2.4 |

**成本为什么是唯一能跨轮的**：它由 `单价 × token 量` 构成，而单价是**配置决定的常量**，
不随批次漂移。token 量的轮次波动（±2 倍）远小于单价差（5–15 倍），所以两列永远不会撞上。
其余指标（步数、token、措辞）都直接由模型的**当轮行为**决定，都会被批次效应打穿。

### 2.3 批次效应警告（判定时必做的一步）

> **如果一次 `eval_run_dual` 里的两列差异，小于同套件的历史轮内散度，
> 判定为「在批次噪声范围内，不显著」。**

即：差异不跨过一个**从历史数据算出的噪声底**，就不许下结论。
这条把"看起来有差异"和"差异超出了噪声"分开，是防止 v1 那种误判复现的机制。

**示例（03 步数）**：若历史轮内散度是 2 步，而本次跑到 pro 5 / flash 6，
差 1 步 < 2 步 → 判定"不显著"，**不出结论**。

### 2.4 步数为什么直接不判定

**步数不稳定 + 不进判定 = 没有存在价值**（v3 数据出来后确认，见第八节）。
它在设计里只保留两个用途，都是**诊断**不是**判定**：

1. 发现异常漂移（如候选步数突然翻倍 → 提示可能重试循环）
2. 成本变化的归因（成本变化来自单价还是来自行为）

**绝不设阈值。** 不只是"不能跨模型复用"——是根本不该写死。三批次数据显示
步数可以整体平移、且**方向会翻转**，任何固定阈值（"≤7 步通过"）都会误判。

### 2.5 v1/v2/v3 批次效应实证

三批次相隔约 20 分钟，代码、prompt、模型、采样量完全相同（数据见
`docs/backend-comparison.md` 第八节）：

| 指标 | 三批次一致性 |
|---|---|
| 步数 | **不稳定**：03 三批三个判定、05 三批两个判定 |
| 成本 | **稳定**：5 套件 × 3 批次 = 15/15 判定完全一致 |

**同一配置、三批三个判定**，而批次之间没有任何已知的差异。这是批次效应的典型形态：
n=3 的"区间不重叠"只看轮内散布，**对轮间漂移毫无抵抗力**。

所以：
- **加大 n 不能解决**——得在同一轮内加，且要能识别轮间漂移；单纯从 3 加到 5 只是
  把同一次漂移测得更精确。
- **唯一可靠做法是两列在同一轮内相邻采样**（当前实现已是：每组内 baseline 与
  candidate 相继执行），且**只看两列的轮内相对关系**。

### 2.6 其余采样约束

**跨套件不能复用同一次运行的数据**：`workspace` 是共享的，每个套件跑之前必须
`fixtures/reset-all.mjs` 重置，否则第二个后端看到的是第一个后端改好的文件、步数塌成 1。

## 三、判定输出（最终版本，2026-09-28；3.2/3.3 已按 v1.1 探针实测更新）

三档，**按顺序短路判定**：

```
① 质量门有失败项？          → 不可迁移
② 兼容性门有失败项？        → 不可迁移（一票否决，与质量门/成本门无关）
③ 兼容性门有未检测项？      → 有条件迁移（把未检测项列进风险清单）
④ 其余（两个门全过）        → 可迁移，成本门决定"值不值得迁"
```

| 判定 | 条件 |
|---|---|
| **可迁移** | 质量门 ✅ 且 兼容性门 **全部已检测且通过**；成本门通过与否只影响建议 |
| **有条件迁移** | 质量门 ✅ 且 兼容性门无失败项，但**存在未检测项**（或成本门未通过） |
| **不可迁移** | 质量门有失败项，**或**兼容性门有失败项 |

报告必须附带两份清单：

- **回退用例清单**：产物判据失败的项（哪个套件、哪条判据、期望 vs 实际）
- **兼容性风险清单**：失败项 + **未检测**项

### 3.1 关键设计：「未检测」不等于「通过」

三态是 `pass` / `fail` / `not_checked`，**`not_checked` 在报告里的渲染与 `pass` 必须能一眼分开**：

| 状态 | 报告渲染 |
|---|---|
| `pass` | `✅ 通过` |
| `fail` | `❌ 失败` |
| `not_checked` | `⚠️ 未检测` |

不能只靠颜色区分——报告是纯文本。措辞本身就要不同。

### 3.2 `cache_control 使用`：静态不可判定 → **v1.1 探针已验证**

> **本节状态**：v1.0 时这一项恒为 `not_checked`（下节「为什么静态判不了」是当时
> 的论证，仍然成立，也正是探针存在的理由）。**v1.1 已用探针请求把它变成 `pass`** ——
> 实测部分见本节末尾。原始论证保留，因为它解释了探针**为什么必须发请求**。

关于兼容性门实现后的预期，有一个**必须纠正**的判断：

> ~~「兼容性门实现后，当前数据下判定会从 `有条件迁移` 变为 `可迁移`（假设两项都通过）」~~

**这个预期在 v1.0 不成立，因为 `cache_control 使用` 这一项静态判不了：**

- `cache_control` 不在任何配置文件里 —— 它由 pi-ai 在 `anthropic-messages` 协议下
  **运行时生成**（系统块 / 末条消息 / 末个工具），retention 默认 `short`，每次请求必发。
  所以「扫配置里有没有 `cache_control`」这个做法会恒返回"没扫到"，
  而实际上它**每次都在发** —— 那会是一个**假通过**，比不检查更糟。
- 端点收到后**是否真的据此建立前缀缓存**，只有发一次请求看计费才能验（= 方案 B 探针）。

**旁证（v1.0 时只有它，而且它自己就不稳定）**：按
`(cost×1e6 − hit×inT − out×outT)/(miss − hit)` 反解"有多少 token 落在 miss 档"：

| 观测 | 输入 token 命中率 |
|---|---|
| v3 三批次 30 次内层运行 | **94.2% – 98.8%**（pro 95.3–98.8，flash 94.2–97.6） |
| 一次相隔数小时的孤立运行（兼容性门 e2e） | **pro 0.0%**（成本 0.004050 = 恰好等于全价的理论值 0.0040498）、flash 30.2% |

**所以"该端点兑现前缀缓存"是真的，但"缓存总是有效"是假的。** 前缀缓存有 TTL，
冷启动必然全价 —— 批次内连续跑几乎全命中，隔几小时单跑就是 0%。这本身就是
**又一个跨轮不可比的量**，与批次效应同源。

#### v1.1 实测：探针把这一项变成了 `pass`（2026-09-29，真实端点）

探针（`src/cache-probe.ts`）在 `https://api.deepseek.com/anthropic` 上真发 4 个请求，
两分支对照、每次前缀约 2.5k token、冷热之间等 2s（等待的理由见该文件头）：

| 路由 | 分支 | #1（冷） | #2（热） |
|---|---|---|---|
| `deepseek-flash` | 带 `cache_control` | 200 · `cache_read=0` | 200 · **`cache_read=2304`** |
| `deepseek-flash` | 对照（不带） | 200 · `cache_read=0` | 200 · **`cache_read=2304`** |
| `deepseek-v4-pro` | 带 `cache_control` | 200 · `cache_read=0` | 200 · **`cache_read=2560`** |
| `deepseek-v4-pro` | 对照（不带） | 200 · `cache_read=0` | 200 · **`cache_read=2560`** |

**四条无一是 4xx** —— 端点接受 `cache_control`，harness 那三次必发的标记不会把请求打回去。
`cache_write` 全程为 0（该端点不单列写入档，不额外收费）。

**同时它坐实了 v1.0 只能"归因不了"的那件事：命中跟标记无关。**
同一路由内，带标记与不带标记的 `cache_read` **逐字节相同**（flash 2304 / pro 2560）。
对照分支根本没有发 `cache_control`，照样命中 —— 所以那 94–99% 的命中率来源是
**端点的自动前缀缓存**，`cache_control` 标记的**边际贡献为零**。

这对判定的影响是**正面的**：成本门里"flash 低 53–78%"这个结论不依赖一个可能被丢掉的字段，
它建立在该端点无条件生效的自动缓存上。因此本项 **`pass`，且不进风险清单**。

> **两个必须一起说的边界**（否则上面的 `pass` 会被读过头）：
> 1. **缓存"有没有"和"有多少"是两回事。** 探针验的是前者；后者受 TTL 影响剧烈波动
>    （见上表 0.0% vs 94–99%），仍然**跨轮不可比**。
> 2. **探针测的是最小请求**（前缀约 2.5k token、单轮、非流式）。真实运行里前缀更长、
>    多轮增长、且是流式 —— 探针不覆盖那些条件下的行为。

### 3.3 当前数据下的完整判定

| 门 | 结果 |
|---|---|
| 质量门 | ✅ 54/54 产物判据通过（三批次，82/82 快照复核一致） |
| 兼容性门 | ✅ `system 字段格式` pass、`cache_control 使用` **pass**（v1.1 探针已验证） |
| 成本门 | ✅ flash 低 53–78%（n=9，15/15 判定一致） |
| **判定** | **可迁移** —— 风险清单里不再有 ⚠️ 项（只剩成本门那条 ℹ️，它恒在） |

**v1.0 时这一格是「有条件迁移」**，因为探针还没做。v1.1 补上之后，判定第一次
出得了「可迁移」—— 而这正是 1.0.0 那节"已知限制第 1 条"点名的缺口。

## 四、产物断言：已实现 ✅

> 本节原为「前置条件：当前缺失的产物断言类型 ⚠️」。**2026-09-28 已实现并接线**，
> 实现文件 `src/artifact-assert.ts`，接线点 `src/eval-runner.ts` 的 `checkAssertions`。
> 下面保留原始需求分析，再记录实际交付的形态与差异。

### 4.1 原始缺口（已解决）

`checkAssertions` 原先只认 `output_contains` 和 `max_steps`，**没有一种能查工作区产物**，
而 5 个套件验证任务是否做对靠的全是产物（02 的 `slugify.mjs` 输出、03 的 `PASS`、
04 的 `report.json`、05 的 `FAILURE.md` 与缺失的 `deploy.json`）。

`output_contains` 顶不上：模型最后那句话的措辞会变（05 上已见三种写法），
拿措辞当判据就是把随机性写进断言。

### 4.2 实际交付的断言类型（6 种）

原设计了 3 种，实现时发现 `file_exists` 的对偶要拆成两个类型才表达得干净，又补了
`file_content_contains`（05 需要「报告存在**且点出了原因**」，只查存在不够）。
最终 6 种，**都是 5 个套件当前真正用到的**：

| 类型 | 字段 | 用在哪 |
|---|---|---|
| `file_exists` | `path` | 05：`FAILURE.md` 必须存在 |
| `file_not_exists` | `path` | 05：**`config/deploy.json` 必须不存在**（防编造） |
| `file_content_contains` | `path`, `text` | 05：报告里必须提到 `deploy.json` |
| `file_json_equals` | `path`, `value` | 04：`report.json` 语义等于 `{topSku:"B-207", qty:48}` |
| `command_output_contains` | `command`, `text` | 03：`node main.mjs` 输出含 `平均 20.00，最高 30` 与 `PASS` |
| `command_output_equals` | `command`, `text` | 02：`node slugify.mjs` 输出恰好 `hello-world` |

**没有实现用不到的**（如 `file_content_equals`、正则匹配、JSON 路径查询）——
按需再加，不加投机性接口。

`file_json_equals` 走**解析后深比较**（键序无关、空白无关），不是字符串相等。
实测依据：模型写出的是 `{"topSku": "B-207", "qty": 48}`（键值间有空格），
与真值字符串不等但语义相同，字符串相等会把**正确的产物判成失败**。

### 4.3 安全边界（三层）

原来只写了"限制在工作区内、白名单命令"。实际实现成三层：

1. **`shell: false`** —— 命令直接 `spawnSync` 执行，shell 元字符全部失效，
   没有命令拼接面。
2. **解释器白名单 + argv 形状检查** —— 只允许 `node`，且 `command` 必须**恰好两个**
   字符串（`["node", "<工作区内脚本>"]`）。这挡掉了 `node -e "<任意代码>"` 这类
   把断言变成任意命令执行的写法。
3. **路径必须落在工作区内** —— `path` 与脚本路径都做 `resolve` + `relative` 检查，
   越出 `workspace` 直接判失败（不是跳过，是**失败**）。

另有 `MAX_READ_BYTES = 1 MiB`、`COMMAND_TIMEOUT_MS = 20s`、反馈信息里内容截断到
240 字符，防止断言本身变成资源入口或把大段内容灌进报告。

**残留风险（无法在这一层防御）**：工作区里的脚本是**模型改过的**，断言执行它就等于
执行模型写的代码。这与"允许 agent 在工作区里跑代码"是同一件事，属于套件的固有边界，
不是断言引入的。02/03 用的 `slugify.mjs` / `main.mjs` 是 fixture 自带的自检入口，
且 03 的判据刻意查**描述文本**而非 `PASS`，正是为了挡住"改 main.mjs 的期望值骗过自检"。

### 4.4 工作区未声明时的行为

用了产物断言但套件没有顶层 `workspace` → **断言直接判失败**，报
`需要套件顶层声明 workspace`，**不回退到 `process.cwd()`**。
静默回退会在错误的目录里查文件、得到看似有效实则无意义的通过。

### 断言的执行时点

断言在 `runOneBackend` 内、每个 step 的内层运行结束后立即执行——**此时工作区就是
该后端的产物**（baseline 的断言在 candidate 开始前跑完）。所以产物断言天然可用，
不需要等快照。

快照的作用不同：它是**留证**，用于人工复核与跨运行对比，不是断言的数据源。

## 五、兼容性检查项（已实现 ✅）

实现文件 `src/compatibility-check.ts`。**静态检查、零 token、不发请求。**
接线点 `src/index.ts` 的 `execute`：跑双后端**之前**执行 —— 所以即便两个后端
因缺 key 被跳过，兼容性段照样有内容。

### 5.1 ⚠️ 两条原始设计前提被实测推翻

初稿的两个检查项是「读 profile 配置，看 `system` 是字符串还是数组」「扫配置里有没有
`cache_control`」。**核实后发现这两条在本 harness 上都不成立**，照写会得到假结论：

| 初稿前提 | 实际情况 | 证据 |
|---|---|---|
| `system` 是内容块数组 → 会 400 | **恒为数组，且工作正常** | pi-ai 在 `anthropic-messages` 下**无条件**把 system 构造成 `[{type:'text',...}]`（`anthropic-messages.js` 的 `context.systemPrompt` 分支），没有"字符串形态"可选；`AnthropicMessagesCompat` 里也**没有**控制 system 形状的开关。而三批次 **90 次内层运行全部成功**打到 `api.deepseek.com/anthropic` —— **实测证伪**。 |
| 扫配置里有没有 `cache_control` | **配置文件里永远没有** | 它是**运行时生成**的（`getCacheControl()` 默认 `{type:'ephemeral'}`），每次请求必发。扫配置文件恒返回"没扫到"，会对一个真实存在的字段报"通过"。 |

另外 `dsh --dump-config` 的完整 379 行组合配置树里，**`system` 和 `cache_control` 两个键都不存在**
（`system-prompt` 那行只有 `personaPrefix`/`personaSuffix`）。

### 5.2 实际实现的两个检查项

| 检查项 | 判什么 | 状态取值 |
|---|---|---|
| `system_field_format` | **harness 发什么 vs 端点声明收什么**是否对得上 | `pass` / `fail` / `not_checked` |
| `cache_control_usage` | `cache_control` 是否被端点兑现 | `pass` / `fail` / `not_checked`（v1.1 起由**探针请求**判定） |

**检查项一为什么能判 `fail`**：两边都是静态可见的事实 —— harness 侧读 pi-ai 源码
（恒发内容块数组），端点侧看 `baseUrl` 是否自称 Anthropic 兼容（主机或路径带
`anthropic`）。两者对不上**就是确定的配置错误**（把 Anthropic 形状的请求体发往非
Anthropic 端点），证据足够，所以判 `fail` 而不是 `not_checked`。

**检查项二为什么必须发请求**（v1.0 时恒为 `not_checked`，v1.1 补齐）：见第三.2 节。
它在 v1.0 是设计**有意**的保守，不是没写完 —— 报告里明确写出「差一次探针请求」，
而不是假装通过。v1.1 补上后这一项才第一次能取到 `pass`/`fail`，
**而它在"没探成"时依然诚实地退回 `not_checked`**（没密钥 / 关掉本项 / `DSH_EVAL_NO_PROBE=1`）。

### 5.3 YAML 开关

套件 YAML 顶层，**两项默认都开**：

```yaml
compatibility:
  check_system_field_format: true
  check_cache_control: true
```

关掉一项会让它变成 `not_checked`（**不是** `pass`）—— 用户能说"我知道这项没问题"，
但不能说"这项算通过了"。判定因此最多到「有条件迁移」，未检测项列进风险清单。

### 5.4 后续补入的项

~~**v1.1 的探针请求**（方案 B）~~ → **已交付**（2026-09-29）：它是让 `cache_control 使用`
从 `not_checked` 变成 `pass`/`fail` 的**唯一**途径，也是「可迁移」判定的唯一缺口。
实测结果见第三.2 节，实现与边界见 [`docs/v1.1-release.md`](v1.1-release.md)。

仍待定（不在本期）：工具调用格式差异、`stop_reason` 语义差异、并发/限流行为差异。

## 六、当前数据支持什么 / 不支持什么

### 支持

- **质量门在当前套件池上通过，且现在是自动判定的。** 三批次共 9 次对比
  × 2 后端 = 90 次内层运行，产物判据 **54/54 全对**（01 无工作区，不计）；
  免费复核脚本对跨三批次累积的 **82/82 份快照**独立确认。
  v2 的 15/15 由 `src/artifact-assert.ts` 自动判定，与人工核对**零分歧**。
  flash 在四个可解任务上全部正确完成，在不可解任务上正确报失败且**零编造**。
- **成本门通过，且是唯一跨轮稳定的指标。** 三批次合并 n=9，逐套件省 **53–78%**；
  5 套件 × 3 批次的判定 **15/15 完全一致**，无一例外。
- **步数门删除是对的——三批次数据各给了一次证明。**
  03 上三批给出三个判定：v1 不重叠（pro 多）、v2 不重叠（flash 多）、v3 重叠。
  若把步数写进判据，这里会**两次误报，且方向相反**。
- **产物判据 n=1 够用。** 三批次共 54 份产物判据无一例外。

### 不支持

- **套件池不覆盖编码场景的完整谱系。** 当前 5 个套件是"单步问答 / 单文件修复 /
  多文件定位 / CLI 解析落盘 / 失败报告"。**没有覆盖**：长上下文（>100k）、
  多轮对话、大范围重构、并发工具调用、真实仓库规模的任务。
  → **接受门的适用范围必须声明为「当前套件池覆盖的任务类型」**，不能读成"这两个模型
  在任何任务上等价"。
- ~~**兼容性门已实现，但当前数据下仍不可能输出「可迁移」**~~ → **v1.1 起可以了**：
  `cache_control 使用` 由探针请求判定（见第三.2 节），实测 `pass`，于是判定到得了「可迁移」。
  但**只有在探针真跑成时**才是这样 —— 没密钥 / 关掉本项 / `DSH_EVAL_NO_PROBE=1`
  时它仍退回 `not_checked`，判定仍最多「有条件迁移」。
- **步数与 token 指标不具备跨轮可复现性。** v1 与 v2 之间，03 的步数差异
  **方向反转**，05 的步数判定反转，01/02 的输出 token 判定也反转。
  → 任何基于单轮 n=3 的步数/token 结论都不可靠，**门槛值尤其不能用**。
- **只有 1 对模型的数据。** "成本差异稳定、步数差异不可复现"这个模式是否普遍，
  需要再跑一对（如 v4-pro vs Claude）才知道。
- **05 的基线散度未被解释。** v1 里同一任务在 pro 上步数 6–10、输入 token 差 2 倍，
  v2 里变成稳定 6 步。原因未查明。在查清之前，05 不适合承担任何**步数相关**的判据。
- **无跨模型的价值判断。** 本门只回答"能不能换"，不回答"该不该换"。
